# 功能交付流程

## 启动、范围与续跑

- **触发**：仅在用户明确调用 `feature-workflow`（如 `$feature-workflow`、`/feature-workflow`）或要求使用本流程时启动；继续同一流程无需重复调用。
- **边界**：先确定用户要求做到哪一步。只讨论或评审时保持只读；只定验收标准或只写 E2E 用例时停在对应阶段；用户明确要求“先确认再改”时保留确认点。
- **单一依据与记录**：已确认的验收标准（AC）是业务行为的唯一依据，工单、审查、测试和验收均引用其中的 `spec_id` 与 `AC-01` 等编号（跨功能集中引用记为 `<spec_id>:AC-01`）。**不生成 `docs/specs/*.spec.md` 类独立 Spec 文档**；过程记录优先沿用项目既有工单/PR 或直接在回复中维护，仅在用户明确要求落盘记录时按 [交付记录模板](references/feature-record.md) 整理。涉及权限、数据写入规则、接口契约或跨模块依赖时展开设计，并在实现前由相关负责人确认受影响的约定。
- **Midscene E2E 测试文件（`.spec.ts`）**：需要页面/端到端验证或纳入全局集中测试的功能，**明确生成或更新独立的 Midscene E2E 测试文件**（优先沿用项目 Playwright/Midscene E2E 目录，无约定时默认落盘到 `e2e/<spec_id>.spec.ts`），文件名前缀须与唯一英文 `spec_id`（kebab-case 或工单号）严格一致；新建前先检查目录避免重名覆盖。**编写或修改 `.spec.ts` 前必须先读取 Midscene 使用文档与项目 fixture 约定**，禁止凭记忆臆造 API。
- **续跑**：接手时先核对当前阶段、已确认的 AC、关联的 `e2e/<spec_id>.spec.ts`、候选版本和已有证据，从第一个缺少有效产出或证据的阶段继续。

## 交付阶段

1. **需求评审**
   - 核查现有需求、相关代码和项目约定，区分：已确认事实、可逆实现假设、需用户决定的业务问题。
   - 明确目标、范围、不做什么、依赖与决策人；关键未决问题给出选项、影响和建议，必要时按 `grilling` 澄清。
   - 已明确部分可先起草 AC；未决项只阻塞依赖它的定稿与实现。

2. **验收标准（AC）与测试计划**
   - 确定唯一英文 kebab-case 或工单号 `spec_id` 与 `AC-01` 等编号；用可观察行为编写 `AC`（编号、是否必验、前置条件与操作、预期、验证方式），覆盖正常、失败与边界场景（直接在回复或既有工单中维护，不额外新建 `docs/specs/*.spec.md`）。
   - 借鉴 `to-spec`：优先在现有页面交互或公开接口上验证行为。
   - 需页面/E2E 验证或纳入集中测试时，开发前确定目标 Midscene E2E 文件路径（默认 `e2e/<spec_id>.spec.ts`，新建前先查重确认是新增还是追加迭代），并按 AC 记录目标环境、角色/测试账号、测试数据、Midscene/Playwright 运行前提、准备人与验收人，缺项标明补齐人。
   - 开发前确认必验项与测试入口（后续直接作为 `tdd` 的 pre-agreed seams，不重复确认）；已有明确依据的不重复询问。每项必验 AC 须可独立判定且有可行验证安排；准备未齐不阻塞无依赖工作。

3. **设计与拆分**
   - 核对受影响模块、接口和可复用能力；记录影响兼容性、数据、权限或联调的设计决定。涉及 UI 设计时接入 `impeccable shape`。
   - 涉及代码改动时，开发前明确：最终审查的 Git 比较基线、候选版本交付形态（`工作区交付` 或 `已授权提交/PR`）、已确认 AC 来源（工单/PR/对话记录等）；未确定项记为待确认。
   - 借鉴 `to-tickets`：按可单独演示或验收的用户行为纵向拆分，每项包含所需各层改动与验证，引用 AC 并列明实际阻塞依赖；小需求可合并为一项。
   - 所有必验 AC 有归属后，优先推进无未完成依赖的任务；仅在改动边界清楚且允许委派时并行。

4. **实现与自查**
   - 按已确认 AC 实现；关键行为和可自动化缺陷回归按 `tdd` 执行。
   - 涉及页面/端到端或全局集中测试的 AC，按下文 **Midscene E2E 测试（`.spec.ts`）** 要求**先读取 Midscene 使用文档与项目 fixture，再生成或更新 `<e2e_dir>/<spec_id>.spec.ts`**。
   - 在新增/更新的测试用例描述（含 Midscene `.spec.ts` 的 `test.describe` / `test` 标题）中统一标注 `[<spec_id>:AC-01]`（整组用例标注 `[<spec_id>]`），确保后续可按 `spec_id` 集中筛选执行。
   - 对照 checklist 做实现自查，逐项比对与已确认 AC 的差异，检查遗漏、额外行为和回归风险。
   - 只修实现错误回到本步；若改变已确认行为，先获确认更新 AC，再同步工单、测试（含 `.spec.ts`）和验收项。

5. **正式验证**
   - 先跑定向测试（含关联的 `<spec_id>.spec.ts` Midscene E2E 用例；若当前环境缺少模型配置或浏览器前置条件，记录缺口并标明补验人），再在候选交付版本上跑项目要求的完整质量检查；从 `README.md`、`tests/README.md`、`package.json` 或 CI 配置核对当前命令与覆盖范围，优先复用既有完整检查（如 `quality:ci`）。
   - 需要真实浏览器、宿主微应用、后端联调或账号权限的场景，在对应环境实测；单测和启动冒烟只能证明其实际覆盖的行为。
   - 记录候选 commit 或受测工作区状态、验证环境和报告；定时 CI 仅在确认对应候选版本时有效。

6. **审查与逐项验收**
   - 对最终候选版本做代码审查，有用户可见 UI 改动时同步做 UI 审查。
   - 对照 checklist 为每条 AC 填 `通过`、`失败`、`阻塞` 或 `未验证`；`通过` 须有证据覆盖预期及约定的必需验证方式。
   - 只做验收时，在授权范围内补证并逐项更新；发现问题先报告，是否修复按用户授权决定。
   - 验证后改动代码、`.spec.ts` 测试、已确认预期或相关环境时，重新审查并验证受影响项，确保完整质量检查对应最终候选版本（若项目另有独立记录文档，仅回写验收/交付记录不触发重审）。
   - 按下方规则给出整体验收结论。

7. **交付**
   - 汇总并记录 `spec_id`、Midscene E2E 文件路径（`e2e/<spec_id>.spec.ts`，如有）及执行命令、实际交付版本、验收与质量报告、已知问题及后续动作。
   - 需部署时补充产物、目标环境、回滚步骤和发布后验证项，按用户授权及项目规则执行。
   - 明确区分并分别报告状态：`可交付`、`已合并`、`已部署`、`发布后验证通过`。需要 PR 正文或复盘时按下文处理。

## 按 `spec_id` 集中测试（E2E 全局回归）

- 用户指定一个或多个 `spec_id` 或发起全局 E2E 集中测试时，在项目 E2E 目录（默认 `e2e/`，支持 `**/<spec_id>.spec.ts` 与 `**/*.spec.ts` 检索）定位对应的 Midscene `.spec.ts` 文件。
- 按文件路径（如 `npx playwright test e2e/<spec_id>.spec.ts`）或统一标题标记（如 `--grep "<spec_id>"` / `[<spec_id>:AC-01]`）批量执行 Midscene E2E 及相关自动化测试；缺少对应 `.spec.ts`、Midscene 文档/fixture/模型配置或运行环境时，按 `spec_id` 标明缺口。
- 按 `spec_id` 汇总输出测试结果（通过/失败/阻塞/未验证及证据）。

## 验收阻塞规则

满足任一条件即**阻塞整体验收**，须逐项记录原因、负责人和解除条件：

- 任一必验 AC 非`通过`（`失败`、`阻塞`或`未验证`）或缺少约定的必需证据。
- 候选版本的项目完整质量检查失败或未在最终候选版本上运行。
- 所需正式审查或业务签核未完成（其中，`提交/PR` 交付若仍有未提交的代码或 `.spec.ts` 测试改动，仅算工作区预审，正式审查仍未完成；明确约定为`工作区交付`时，须完成覆盖工作区改动与相关未跟踪文件的双轴审查）。
- 审查确认存在影响必验行为、权限、数据或兼容性的未解决问题。

不影响已确认标准的体验或维护建议跟踪到后续。若需调整约定的验收标准，须由有权决定人明确确认并更新 AC 及相关 `.spec.ts` 用例，记录影响与重验范围、保留原失败或缺证记录，且不得绕过项目强制门禁。

## 配套 Skill 与文档衔接

进入对应阶段时，按名称读取当前环境可用的 `SKILL.md` 并沿用其适用条件与批准要求（下文命令名用于选择 Skill 内部流程，不是终端命令）。若找不到对应 Skill、审查工具不可用或配置缺失，按本节要求的目标产出执行等价检查并注明缺口，继续独立可做的工作。`to-spec`、`to-tickets`、`retro` 方法已内化，仅用户另行要求时运行原版；提交、建分支/PR、写外部工单均须用户授权。

- **需求澄清（`grilling` / `domain-modeling`）**：仅在未决业务问题实质改变范围或行为时使用 `grilling`；先用代码和文档解决事实问题，只问前沿未决项并附建议；UI 问题转 `impeccable shape` 并复用已确认答案。新业务术语或长期领域决策需沉淀时，在授权范围内用 `domain-modeling` 更新 `GLOSSARY.md` 或 ADR。
- **UI 设计（`impeccable` `shape`）**：面向新增或变更界面的布局、交互与视觉设计，传入目标界面、已确认 AC、现有设计和待决项。`shape` 仅产出设计简报并停在确认，不写代码；后续修改 UI 前按 `impeccable` 要求读取 `craft-floor.md`。已确认方向和关键状态写入设计记录，涉及可观察行为的新决定回写 AC。
- **开发与排障（`tdd` / `diagnosing-bugs`）**：用 `tdd` 复用阶段 2 已确认测试入口作为 pre-agreed seams，逐条 AC 垂直切片（先写失败测试 → 最小实现 → 复跑）；优先复用项目现有测试框架与约定，低影响改动不为走流程加测试，重构留到审查阶段。难稳定复现的问题先用 `diagnosing-bugs` 建立稳定失败反馈环并最小化复现，再修复并保留有效回归测试。
- **Midscene E2E 测试（`.spec.ts`）**：编写或修改任何作为全局 E2E 测试的 Midscene `.spec.ts` 前，**必须先按以下顺序读取使用文档，禁止凭记忆臆造 API、fixture 名称或参数签名**：
  1. 项目内 Midscene / E2E 文档、`playwright.config.*`、自定义 fixture 文件（如 `./fixture`）与现有 `.spec.ts` 示例。
  2. `node_modules/@midscene/*` 中的 README 与 TypeScript 类型定义、当前环境已安装的 Midscene 相关 Skill，或官方 Midscene 文档（Playwright 集成 `https://midscenejs.com/integrate-with-playwright.html` 与 API `https://midscenejs.com/api.html`）。
  - 文件落盘到 `<e2e_dir>/<spec_id>.spec.ts`（默认 `e2e/<spec_id>.spec.ts`），作为全局 E2E 集中测试文件；按项目 fixture 约定导入（如 `import { test, expect } from "./fixture"`，使用实际导出的 `aiTap`、`aiAssert` 等 API），在 `test.describe` / `test` 标题中标注 `[<spec_id>]` / `[<spec_id>:AC-01]`，覆盖可观察页面行为与防回归断言。
  - 若项目尚未接入 Midscene、缺少 fixture 或文档不可读，先明确报告缺口，不擅自安装依赖或臆造调用方式。
- **最终代码审查（`code-review`）**：有代码改动时按 **Standards** 与 **Spec** 两轴审查，优先使用两个独立上下文 subagent 并行执行（不可用时注明降级为单上下文串行），分别记录结论。
  - `提交/PR` 交付：确认基线有效、`HEAD` 对应候选提交、差异非空且覆盖全部待交付代码改动；存在未提交的代码或 `.spec.ts` 测试改动时仅做工作区预审，正式审查保持待补。
  - `工作区交付`：对 `git diff <基线>` 及相关未跟踪文件执行同等双轴审查并标注为工作区审查（若后续转为提交/PR 交付，须在最终提交上复审）。
  - 提供明确的 AC / 需求来源（工单、PR、已确认 AC 文本或相关文件）；缺基线、需求来源或 tracker 配置时注明缺口并继续能做的检查，不为凑齐审查自行提交、切换分支、初始化 tracker 或发布本地文档。
- **最终 UI 审查（`impeccable` `audit` / `critique`）**：有用户可见界面改动时，运行 `impeccable audit` 做技术质量检查（a11y、性能、主题、响应式、实现完整性；原生端走 `audit.native.md`），并对照已确认设计与 AC 核对布局、交互和关键状态；涉及新页面或较大改版需 UX/视觉评审时补跑 `critique`。记录发现、验证方式与证据（浏览器/视口/手势等）及未验证场景；纯逻辑改动省略。
- **PR 与复盘（`pr` / `retro`）**：写 PR 正文时用 `pr` 组织 Summary、Before/After 证据与 Merge Danger。明显返工或交付阻塞后，借鉴 `retro` 提炼一条防重演改进（可机械判断的优先补自动化检查，需人工判断的补项目约定），记录建议与负责人。
