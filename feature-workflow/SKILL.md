# 功能交付流程

仅在用户明确调用 `$feature-workflow` 或要求使用本 Skill 时启动；继续处理同一个已主动发起的流程无需重复调用。先确定用户要求做到哪一步。只讨论或评审时保持只读；只写 Spec 时停在 Spec。用户明确要求“先确认再改”时，保留这个确认点。需要新建或补齐记录时，使用 [交付记录模板](references/feature-record.md)。在已授权的记录中更新当前阶段、已确认的 Spec 版本、候选版本、阻塞与负责人、下一步。接手时先核对版本和证据，从第一个缺少有效产出或证据的阶段继续。

把已确认 Spec 作为业务行为的依据；工单、代码审查、测试和验收证据引用其中的 `AC-01` 等编号。简单需求在同一份记录中写 Spec、实现计划和验收结果；涉及权限、数据写入规则、接口契约或跨模块依赖时，展开相应设计，并在实现前由相关负责人确认受影响的约定。

## 从需求到交付

1. **需求评审**：查现有需求、相关代码和约定，区分已确认的事实、可逆的实现假设和需要用户决定的业务问题。确定目标、范围、不做什么、依赖与决策人。关键问题记录选项、影响和建议，必要时按下文澄清。已明确的部分可先写 Spec 草案；未决项只阻塞依赖它的定稿和实现。
2. **制定 Spec 与验收 checklist**：用可观察的行为写 `AC`，说明前置条件、操作、预期和验证方式；覆盖相关的正常、失败和边界场景。借鉴 `to-spec`：优先在现有的页面交互或公开接口上验证行为。需要浏览器实测或联调时，开发前按 AC 记录目标环境、所需角色或测试账号、测试数据、准备人与验收人（按实际需要填写）；缺项记录谁补齐。开发前确认必验项和所需测试入口；已有明确依据的内容不重复确认。每项必验 AC 都须可独立判定且有可行的验证安排，准备未齐不耽误无依赖的工作。
3. **设计与拆分**：核对受影响模块、接口和可复用能力；记录会影响兼容性、数据、权限或联调的设计决定。涉及 UI 设计时按下文接入 `impeccable`。涉及代码改动时，开发前明确最终审查的 Git 比较基线、候选版本是工作区交付还是已授权的提交或 PR、已确认 Spec 的路径或链接；尚未确定的事项记为待确认。借鉴 `to-tickets`：按可单独演示或验收的用户行为拆分，每项包含该行为所需的各层改动和验证，引用 AC 并列出实际阻塞它的任务。小需求可只写一项。所有必验 AC 有归属后，优先推进无未完成依赖的任务；仅在改动边界清楚且允许委派时并行。
4. **实现与自查**：按确认的 AC 实现；关键行为和可自动化的缺陷回归按下文使用 `tdd`。用 checklist 做实现自查，把差异与 Spec 逐项对照，检查遗漏、额外行为和回归风险。若只修实现错误，回到本步；若改变已确认的行为，先更新 Spec 并确认变化，再同步工单、测试和验收项。
5. **正式验证**：先跑定向测试，再在候选交付版本上跑项目要求的完整检查。在 `data-model-ui` 复用 `yarn quality:ci`；从 `README.md`、`tests/README.md` 和 `package.json` 核对当前命令与覆盖范围。需要真实浏览器、宿主微应用、后端联调或账号权限的场景，在相应环境验证；单测和启动冒烟只能证明它们实际覆盖的行为。记录候选 commit 或实际受测的工作区版本、验证环境和报告；定时 CI 的结果仅在确认对应候选版本时可用。
6. **审查与逐项验收**：按下文对最终候选版本做代码审查，有 UI 改动时同时做 UI 审查。对照 checklist 给每条 AC 填 `通过`、`失败`、`阻塞` 或 `未验证`；通过须有证据覆盖预期及约定的必需验证方式。只做验收时，在授权范围内补证并逐项更新；发现问题先报告，是否修复按用户授权决定。验证后改动代码、预期或相关环境时，重新审查和验证受影响的项目，并让完整质量检查对应最终候选版本。按下方规则给出整体验收结论。
7. **交付**：记录实际交付的版本、Spec、验收与质量报告，以及已知问题和后续动作。需要部署时补充产物、目标环境、回滚办法和发布后验证项，按用户授权及项目规则执行；准备好交付、代码已合并、已部署和发布后验证通过分别报告。需要写 PR 或复盘时按下文处理。

## 验收阻塞规则

- 必验 AC 未通过或缺必需证据、候选版本质量门禁失败或未通过验证、所需正式审查或签核未完成，或审查确认存在影响必验行为、权限、数据或兼容性的未解决问题：阻塞整体验收。逐项记录原因、负责人和解除条件。
- 不影响已确认标准的体验或维护建议可以跟踪到后续。若需调整约定的验收标准，由有权决定的人明确确认并更新 Spec，记录影响和重验范围；保留原失败或缺证记录，并遵守项目的强制门禁。

## 按阶段使用其他 Skill

从当前环境可用技能中按名称找到对应的 `SKILL.md`，在进入相关阶段时读取并执行。下面的命令名用于选择该 Skill 中的流程，不是要在终端执行的命令。沿用该 Skill 的适用条件与批准要求；找不到 Skill、审查工具不可用或证据不足时，记录缺口，继续独立可做的检查。`to-spec`、`to-tickets` 和 `retro` 的方法已写入本流程；只有用户另行要求时才运行这些手动 Skill 的原版。Spec 与工单沿用交付记录，提交、创建分支或 PR、写入外部工单均按用户授权执行。

- **需求澄清**：只有未决业务问题会实质改变范围或行为时才用 `grilling`；先用代码和文档解决已有答案的问题，把剩余问题与建议一起提出。涉及 UI 时，把界面问题交给 `impeccable shape`，复用已确认答案。新业务术语或长期领域决策需要单独沉淀时，在授权范围内用 `domain-modeling` 更新词汇表或 ADR。
- **UI 设计**：面向新增或变更界面的布局、交互或视觉设计，使用 `impeccable` 的 `shape` 流程，带上目标界面、已确认的 Spec、现有设计和还需决定的事项。沿用已确认的方向；需要确认新方向时，在确认后再实现。把确认的方向和关键界面状态写入设计记录，涉及可观察行为的新决定更新到 Spec 与 AC。
- **开发与排障**：用 `tdd` 从已确认的测试入口逐项实现关键行为：先写一条针对 AC 的测试，确认它因目标行为缺失或错误而失败，再做最小实现并复跑。优先复用现有 Vitest 测试方式；低影响改动不为走流程而加测试。难以稳定复现的问题先用 `diagnosing-bugs` 建立稳定反馈，再修复并保留有价值的回归测试。
- **最终代码审查**：有代码改动时使用 `code-review`，提供比较基线、候选提交和显式的 Spec 来源（仓库内 Spec 可直接提供路径）。按 **Standards** 与 **Spec** 分别记录结论。确认基线有效、审查时的 `HEAD` 对应候选提交、差异非空且覆盖全部待交付改动。仅交付工作区或仍有待交付的未提交改动时，可对实际工作区预审，正式审查保持待补；缺基线、Spec 或该 Skill 所需的 tracker 配置时，注明缺口并继续能做的检查。不为凑齐审查自行提交、切换分支、初始化 tracker 或发布本地 Spec。
- **最终 UI 审查**：有用户可见的界面改动时使用 `impeccable` 的 `audit`，提供候选版本、目标界面和已确认的设计；同时核对布局、交互和关键状态是否符合设计与 AC。记录发现、验证证据及未验证的浏览器或场景。纯逻辑改动省略本项。
- **PR 与复盘**：需要写 PR 正文时，用 `pr` 组织改动、前后对比证据及合并影响。明显返工或交付阻塞后，借鉴 `retro` 找出一个能避免重演的改进：可机械判断的问题优先补现有检查，需要判断的问题补项目约定；记录建议和负责人。
