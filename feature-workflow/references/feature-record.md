# 交付记录模板

优先沿用项目既有需求文档、工单或 PR 的记录位置。需要新文档且项目没有约定时，可在 `docs/features/<feature-id>.md` 用一份 Markdown 维护。把业务规则写在 Spec，把实现和证据链接到相应 AC；不在多处复制预期。只提取当前阶段所需部分，按实际情况省略可选字段。

```markdown
# <需求标题>

需求来源：<需求链接或明确的用户请求>
续跑记录：<当前阶段；已确认 Spec 版本；当前候选版本或尚无；阻塞与负责人；下一步>

## 需求评审

- 目标：<谁遇到什么问题，期望什么结果>
- 做 / 不做：<范围与边界>
- 决策：<未决问题、影响、决策人，或已确认结论及依据>

## Spec

<用户流程、关键规则、异常行为；必要时补接口、权限或兼容要求。>

| 编号 | 必验 | 前置条件与操作 | 可观察预期 | 验证方式 |
| --- | --- | --- | --- | --- |
| AC-01 | 是 | 编辑数据模型后保存，接口返回失败 | 显示失败提示，保留编辑内容 | 从页面保存按钮触发组件交互测试；真实后端错误响应另行联调 |

确认依据：<用户指示、评审结论或已批准 Spec 的链接 / 版本>
实测准备（按 AC，若需）：<目标环境；账号角色与测试数据；准备人与验收人；尚缺项>

## 设计与实现计划

- <可独立演示的用户行为或工单链接> → AC-01；阻塞依赖：<无或任务编号>。
- 关键设计（按需）：<受影响边界、决定、相关负责人确认记录>
- UI 设计（如涉及）：<目标界面、已确认方向与关键状态>
- 代码审查准备（如涉及）：<比较基线、候选版本形成方式、Spec 路径或链接、待确认事项>

## 验收 Checklist

候选版本 / 环境：<commit 或工作区版本；测试环境和相关账号角色>
完整质量检查：<命令、结果、报告或 CI 链接>
代码审查（有代码改动）：<比较基线、Standards 与 Spec 各自的结论及报告>
UI 审查（有界面改动）：<目标界面、impeccable 审查及设计核对结果>

| AC | 结果 | 证据或缺口 |
| --- | --- | --- |
| AC-01 | 未验证 | <用例及运行结果、实测记录；缺失时写明阻塞和谁补验> |

业务签核（如需要）：<责任人及结论>
整体验收：<通过 / 阻塞；原因、负责人、解除条件；若调整标准，附批准依据和受影响 AC>

## 交付

- 版本 / 产物：<实际提交、PR、构建产物或工作区变更>
- 交付状态：<待验证 / 可交付 / 已合并 / 已部署 / 发布后验证通过，按实际填写>
- 已知问题与后续：<影响范围、处理安排或无>
- 发布（如涉及）：<目标环境、回滚版本或步骤、发布后验证结果>
- 复盘（如需要）：<可防止返工的检查或约定、负责人>
```
