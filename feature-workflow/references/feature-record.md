# 交付记录模板

优先沿用项目既有的工单或 PR，或直接在回复中按需节选维护；**不强制额外新建 `docs/specs/*.spec.md` 文档**。面向全局 E2E 集中测试的独立产物是 Midscene 测试文件 `<e2e_dir>/<spec_id>.spec.ts`（默认 `e2e/<spec_id>.spec.ts`，文件名前缀与唯一英文 `spec_id` 严格一致；**编写前必须先读取 Midscene 使用文档与项目 fixture**）。自动化测试用例（含 Midscene `.spec.ts`）统一在 `test.describe` / `test` 标题中标注 `[<spec_id>:AC-01]` 或 `[<spec_id>]`。仅保留当前阶段所需部分，按实际情况省略可选字段。

```markdown
# <需求标题>

- `spec_id`：<唯一英文标识，如 user-role-permission 或工单号；与 e2e/<spec_id>.spec.ts 文件名前缀严格一致>
- Midscene E2E 用例：<e2e/<spec_id>.spec.ts 或不适用>
- 需求来源：<需求链接或明确的用户请求>
- 续跑记录：<当前阶段；交付形态与候选版本（或尚无）；阻塞与负责人；下一步>

## 需求评审

- 目标：<谁遇到什么问题，期望什么结果>
- 做 / 不做：<范围与边界>
- 事实与假设：<已确认事实；可逆实现假设>
- 决策：<未决问题、选项/影响、决策人，或已确认结论及依据>

## 验收标准（AC）与测试计划

<用户流程、关键规则、异常行为；必要时补接口、权限或兼容要求。>

| 编号 | 必验 | 前置条件与操作 | 可观察预期 | 验证方式 |
| --- | --- | --- | --- | --- |
| AC-01 | 是 | 点击右上角“更多筛选”按钮 | 筛选面板完整可见且不被下方表格卡片遮挡 | Midscene E2E（`e2e/<spec_id>.spec.ts`，标注 `[<spec_id>:AC-01]`） |

- 确认依据：<用户指示、评审结论或需求链接>
- 测试入口 / Seams：<已确认的自动化测试入口、Midscene `e2e/<spec_id>.spec.ts`、集中测试命令如 `npx playwright test e2e/<spec_id>.spec.ts`>
- 实测准备（按 AC，按需）：<目标环境；账号角色与测试数据；Midscene 模型与 Playwright 运行前提；准备人与验收人；尚缺项>

## 设计与实现计划

- <可独立演示的用户行为或工单链接> → AC-01；阻塞依赖：<无或任务编号>
- 关键设计（按需）：<受影响边界、设计决定、相关负责人确认记录>
- UI 设计（如涉及）：<目标界面、impeccable shape 已确认方向与关键状态>
- 代码审查准备（如涉及）：<交付形态（工作区 / 提交或 PR）、Git 比较基线、AC 来源、待确认事项>

## 验收 Checklist

- 候选版本 / 环境：<commit 或工作区状态；测试环境和相关账号角色>
- 完整质量检查：<命令、结果、报告或 CI 链接>
- 代码审查（有代码改动）：<交付形态、比较基线、Standards 与 Spec 各自结论及报告；降级单上下文时注明>
- UI 审查（有界面改动）：<目标界面、impeccable audit（及按需 critique）结果、设计与 AC 核对、未验证场景>

| AC | 必验 | 结果 | 证据或缺口 |
| --- | --- | --- | --- |
| AC-01 | 是 | 未验证 | <通过 / 失败 / 阻塞 / 未验证；附单测、Midscene `.spec.ts` 或实测记录，缺口写明阻塞与补验人> |

- 重验 / 标准变更记录（如有）：<原失败或缺证记录；标准调整的批准依据与重验范围>
- 业务签核（如需要）：<责任人及结论>
- 整体验收：<通过 / 阻塞；原因、负责人、解除条件>

## 交付

- Midscene E2E 用例（如涉及）：<`e2e/<spec_id>.spec.ts` 及集中执行命令>
- 版本 / 产物：<实际提交、PR、构建产物或工作区变更>
- 交付状态：<待验证 / 可交付 / 已合并 / 已部署 / 发布后验证通过>
- 已知问题与后续：<影响范围、处理安排或无>
- 发布（如涉及）：<目标环境、回滚版本或步骤、发布后验证结果>
- 复盘（如需要）：<可防止返工的检查或约定、负责人>
```
