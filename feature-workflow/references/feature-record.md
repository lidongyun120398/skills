# Spec 与交付记录模板

进入 Spec 及后续阶段时，明确生成或更新独立的 Spec 文件。路径优先遵循项目既有的 Spec 目录约定；无约定时默认落盘到 `docs/specs/<spec_id>.spec.md`（`spec_id` 使用唯一英文 kebab-case 或工单号，文件名前缀须与 `spec_id` 严格一致；新建前先查重避免覆盖）。业务规则写在 Spec，实现、测试与证据通过 `spec_id` 及 `AC-01` 关联（跨 Spec 引用记为 `<spec_id>:AC-01`，自动化测试用例描述/标签统一标注 `[<spec_id>:AC-01]` 或 `[<spec_id>]`），不在多处复制预期。仅保留当前阶段所需部分，按实际情况省略可选字段。

```markdown
---
spec_id: <唯一英文标识，如 user-role-permission 或工单号；与 .spec.md 文件名前缀严格一致>
status: draft # draft(起草) -> confirmed(Spec确认) -> verified(整体验收通过) -> delivered(已交付)
spec_version: v1 # 已确认行为发生变更时递增，如 v2
test_entries: [] # 可执行测试文件、命令或过滤标识（如 --grep "<spec_id>"），便于按 spec_id 集中测试
---

# <需求标题>

需求来源：<需求链接或明确的用户请求>
续跑记录：<当前阶段；已确认 Spec 版本；交付形态与候选版本（或尚无）；阻塞与负责人；下一步>

## 需求评审

- 目标：<谁遇到什么问题，期望什么结果>
- 做 / 不做：<范围与边界>
- 事实与假设：<已确认事实；可逆实现假设>
- 决策：<未决问题、选项/影响、决策人，或已确认结论及依据>

## Spec

<用户流程、关键规则、异常行为；必要时补接口、权限或兼容要求。>

| 编号 | 必验 | 前置条件与操作 | 可观察预期 | 验证方式 |
| --- | --- | --- | --- | --- |
| AC-01 | 是 | 编辑表单后保存，接口返回失败 | 显示失败提示，保留已编辑内容 | 页面保存交互测试（标注 `[<spec_id>:AC-01]`）；真实后端错误响应另行联调 |

确认依据：<用户指示、评审结论或已批准 Spec 的链接 / 版本>
测试入口 / Seams：<已确认的自动化测试入口、集中测试过滤标识与实测入口>
实测准备（按 AC，按需）：<目标环境；账号角色与测试数据；准备人与验收人；尚缺项>

## 设计与实现计划

- <可独立演示的用户行为或工单链接> → AC-01；阻塞依赖：<无或任务编号>
- 关键设计（按需）：<受影响边界、设计决定、相关负责人确认记录>
- UI 设计（如涉及）：<目标界面、impeccable shape 已确认方向与关键状态>
- 代码审查准备（如涉及）：<交付形态（工作区 / 提交或 PR）、Git 比较基线、Spec 文件路径、待确认事项>

## 验收 Checklist

候选版本 / 环境：<commit 或工作区状态；测试环境和相关账号角色>
完整质量检查：<命令、结果、报告或 CI 链接>
代码审查（有代码改动）：<交付形态、比较基线、Standards 与 Spec 各自结论及报告；降级单上下文时注明>
UI 审查（有界面改动）：<目标界面、impeccable audit（及按需 critique）结果、设计与 AC 核对、未验证场景>

| AC | 必验 | 结果 | 证据或缺口 |
| --- | --- | --- | --- |
| AC-01 | 是 | 未验证 | <通过 / 失败 / 阻塞 / 未验证；附用例结果或实测记录，缺口写明阻塞与补验人> |

重验 / 标准变更记录（如有）：<原失败或缺证记录；标准调整的批准依据、递增后的 spec_version 与重验范围>
业务签核（如需要）：<责任人及结论>
整体验收：<通过 / 阻塞；原因、负责人、解除条件>

## 交付

- Spec 文件：<`spec_id` 与文件路径>
- 版本 / 产物：<实际提交、PR、构建产物或工作区变更>
- 交付状态：<待验证 / 可交付 / 已合并 / 已部署 / 发布后验证通过>
- 已知问题与后续：<影响范围、处理安排或无>
- 发布（如涉及）：<目标环境、回滚版本或步骤、发布后验证结果>
- 复盘（如需要）：<可防止返工的检查或约定、负责人>
```
